# 10 · AI 运营助手 · 开发任务书

> 给 Cursor 的施工说明。先读 `docs/00-AI-Context.md`、`server/src/modules/ai/*` 再动手。
> 现有 `ai` 模块已有：Laya choice 判类、DeepSeek 写文案、模板兜底、`AiCallLog` 审计、日报 cron（22:00）。本次是**在既有模式上扩展对话能力**，不是重写。

**一句话定义：自建「问经营数据」的只读 AI 助手，模型只负责意图和措辞，数字与权限全部由后端把死。**

---

## 零 · 一页速览

**在现有 NestJS `ai` 模块上扩「商家对话问数」。不是重写，不接 Coze / Dify。**

三层：只读工具层（`AiToolsService`）→ 两段式对话（`POST /ai/chat`）→ 前端悬浮球。平台巡检独立走 cron，不与对话共用通路。

| 交付项 | 内容 |
|---|---|
| 只读工具层 | 营收摘要、券表现、流失会员、现金流提示（一期直接回「尚未接入」） |
| 对话入口 | `POST /ai/chat`，两段式：先出意图 JSON → 再取数 → 模板优先写答案 → 复杂解读才调模型且禁止输出数字 |
| 调试端点 | `/ai-tools/*`（商家侧）；异常商家仅 `PLATFORM` |
| 平台巡检 | cron 与日报同在 22:00；SQL 判异常，模型只写简报，站内信推运营 |
| 配额与审计 | 每日默认 30 次；`AiCallLog` 补 `sessionId` / `intent` / `toolCalls` / token |
| 前端 | Web + 小程序右下角悬浮球聊天面板（仅商家可见） |
| 一期不做 | 语音 ASR（按钮置灰）、写操作、模型写 SQL、改现有业务写接口、Prompt 内塞商家与会员隐私标识 |

**模型挂掉也不能给空白面板**：退化为静态数据卡片（调 `/ai-tools/business-summary` 取昨日数）。

**实施顺序**：先工具拿真数 → 模板对话 → 接模型意图与校验 → 配额审计 → 巡检 → Web 悬浮球 → 小程序悬浮球。

---

## 一、六条铁律（不可协商，违反即返工）

1. **不接 Coze，不接 Dify。** 不要写任何调用外部编排平台的代码，也不要把自己的 API 暴露给外部平台回调。全部在 NestJS 进程内用 function calling 完成。
2. **`merchantId` 只能来自 `@CurrentUser()` 的 JWT 载荷，永远不作为工具参数、请求参数、Prompt 内容出现。** 所有工具函数的签名里不允许有 `merchantId`。
3. **大模型不做算术。** 环比、同比、占比、增量一律在 SQL 或 service 里算完，以字段形式交给模型。模型只负责选口径和措辞。
4. **大模型不碰写操作。** 不新增任何能改动订单、积分、券状态、财务数据的工具。用户要求发积分/核销券时，返回固定引导语，不调用任何工具。
5. **数字不信任模型。** 走模型文案的路径必须做数值校验（见 §4.3），校验不过就回退模板。
6. **平台侧接口与商家侧接口物理隔离。** 跨租户查询只允许 `userType = PLATFORM`，且不得由对话触发，只能由定时任务在进程内调用。

### 2.2 `AiToolsService` 方法（全部强制带 `merchantId` 参数，且只由 service 层内部注入）

| 方法 | 说明 |
|---|---|
| `businessSummary(merchantId, from, to, compare)` | 营收/订单/核销/积分，**返回已算好的 `dodPct`、`momPct`** |
| `couponPerformance(merchantId, days, limit)` | 按券模板聚合，含核销率 |
| `lostMembers(merchantId, limit)` | 超 45 天未到店，按历史消费额降序，**必须分页** |
| `cashflowHint(merchantId)` | 现金流提示。一期无小Z接口，返回 `{ available: false, note: "尚未接入财务诊断" }`，**不要编造** |

> 「券带动客流」口径：核销后 24 小时内同会员产生订单计 1 次，仅统计一次，不做去重归因。写进注释。
>
> **口径待业务确认（先按上述默认实现，抽成常量便于改）：**
> - 券带动客流的归因窗口 —— 默认 24 小时
> - 流失会员判定 —— 默认 45 天未到店（沿用 `templateCopy` 现有文案）
> - 积分超发阈值 —— 默认当月发行面额 > 当月营收 × 30%

### 2.3 HTTP 端点

`POST /api/v1/ai/chat`（JWT + `@Permissions('ai:chat')`）

```jsonc
// 请求
{ "message": "我昨天赚了多少", "sessionId": "可选，不传则新建" }

// 响应
{
  "sessionId": "12-20261026-a1",
  "answer": "昨天营业额 1,240 元，共 18 笔订单，比前天涨了 12.5%。",
  "intent": "revenue_summary",
  "facts": { "revenue": 1240, "orders": 18, "dodPct": 12.5 },
  "card": null,
  "fallbackUsed": false,
  "quota": { "usedToday": 3, "limit": 30 }
}
```

`GET /api/v1/ai-tools/*`（JWT，商家侧，`merchantId` 取自 JWT，**忽略任何请求里传的 merchantId**）

| 端点 | 查询参数 |
|---|---|
| `/ai-tools/business-summary` | `from`, `to`（YYYY-MM-DD）, `compare=prev_period\|prev_month` |
| `/ai-tools/coupon-performance` | `days=7`(1–30), `limit=20`(≤50) |
| `/ai-tools/lost-members` | `limit=20`(≤50), `offset=0` |
| `/ai-tools/abnormal-merchants` | **仅 PLATFORM**，`hours=24`, `limit=50` |

返回体统一 `{ items: [...], meta: { from, to, total, truncated } }`。`truncated: true` 时，对话层要在回答里明说「仅展示前 N 条」。

### 2.4 平台巡检

- 新增 `AiInspectionService`，cron `@Cron('0 22 * * *', { timeZone: 'Asia/Shanghai' })`，**与现有日报共用一个时间点**（不要另起 23:00）。
- **异常由 SQL 判定，模型只写简报**。判定规则实现为独立纯函数，便于单测：

| 规则 | 阈值 |
|---|---|
| 核销暴涨 | 当日核销量 ≥ 近 7 日均值 × 3 且当日 ≥ 10 笔 |
| 深夜核销 | 00:00–05:00 核销占当日 ≥ 60% 且当日 ≥ 10 笔 |
| 零单流失 | 连续 7 天 0 订单，且前 30 天有单 |
| 重复核销 | 同一会员当日核销 ≥ 3 次 |
| 积分超发 | 当月发行积分面额 > 当月营收 × 30% |

- 简报通过 `NotificationService.deliverSystem()` 推给平台运营，正文含**商家 ID 与名称**，`bizType: 'AI_PLATFORM_ALERT'`。
- `prisma/schema.prisma` 的 `NotificationType` 枚举补 `AI_PLATFORM_ALERT`，并写 migration。

### 2.5 审计与限额

- `AiCallLog` 增字段：`sessionId String?`、`intent String?`、`toolCalls Json?`、`tokenIn Int?`、`tokenOut Int?`。写 migration，老数据留空。
- `QuotaService`：进程内 `Map<merchantId:yyyymmdd, count>`，上限读 `AI_CHAT_DAILY_LIMIT`（默认 30）。超限返回 200 + `answer: "今日提问次数已用完，明天再来"`，不抛 429，避免前端报错弹窗。
- 工具调用超时 3s，模型超时 8s（复用 `DeepseekService` 现有 `TIMEOUT_MS`）。任一超时都走模板路径，不让请求挂住。

## 三、对话主流程（`ChatService.chat()`）

```
1. 限流检查 → 超限直接返回限额话术
2. 第一段：DeepseekService.completeJson(intentPrompt, message + 近期上下文3轮)
   → 只允许输出 { intent, params }，intent ∈ 白名单枚举，params 只允许时间与分页
   → 解析失败 / intent 不在白名单 → 走关键词兜底表
3. 后端按 intent 调 AiToolsService（merchantId 在此注入）
4. 第二段：模板优先。
   简单口径（营收/订单/环比）直接用模板拼句子，不调模型；
   需要解读（趋势归因、建议）才调模型写，且 system 里明确"不得输出任何阿拉伯数字"
5. 数值校验：抽出回答里的数字，与 facts 比对；对不上 → 丢弃模型文案，改用模板
6. 写 AiCallLog（含 sessionId / intent / toolCalls）
7. 返回
```

**关键词兜底表**（模型不可用时使用，命中即返回模板，不再调模型）：

| 关键词 | intent |
|---|---|
| 赚 / 营收 / 营业额 / 流水 | `revenue_summary` |
| 订单 / 单量 | `order_summary` |
| 券 / 核销 / 优惠 | `coupon_performance` |
| 积分 | `point_summary` |
| 老客 / 流失 / 没来 | `lost_members` |
| 现金流 / 撑多久 / 资金 | `cashflow` |
| 发积分 / 核销券 / 改价格 / 退款 | `write_request` → 固定引导语，不调工具 |

**拒绝话术（`write_request`）固定为**：「我只做数据查询，不能直接改账。发积分请用扫码录单，核销券请到后台核销页操作。」

## 六、验收标准

1. **越权**：用商家 A 的 token 请求 `/ai-tools/business-summary`，请求体里故意塞 `merchantId=2`，返回的必须是 A 的数据。用商家 token 请求 `/ai-tools/abnormal-merchants`，必须 403。
2. **不编数**：把 `DEEPSEEK_API_KEY` 置空重启，问「我昨天赚了多少」，仍能返回正确数字（走模板）。
3. **不写库**：全流程跑一遍，`orders`/`coupon_codes`/`point_accounts` 无任何写入。
4. **限额**：把 `AI_CHAT_DAILY_LIMIT=3`，连问 4 次，第 4 次返回限额话术且 HTTP 200。
5. **巡检**：seed 一个有「连续 7 天 0 订单」的商家，手动触发 `POST /ai/daily-reports/run`，运营端站内信收到含该商家名的预警。
6. **回归**：`npm run regression` 全绿；现有日报输出格式不变。

## 附录 A · 为什么不用 Coze / Dify（决策记录，勿再讨论）

「智能体」拆开是四件事：意图识别、工具执行、结果编排、会话记忆。Coze 只是把这四件包了层可视化外壳。

本项目已具备后三件（`ai.service.ts` 的 SQL 聚合、`daily-report.ts` 的模板编排、`AiCallLog` 的审计），只缺意图识别与前端入口两块。因此自建成本约 300~500 行，低于接入外部平台并绕开鉴权问题的成本。

**否决 Coze 的硬原因：** 其 HTTP 插件由 Coze 服务端发起请求，Header 只能携带固定值，无法透传终端用户 JWT。若要区分租户，只能把 `merchantId` 作为工具参数交由模型填写，直接违反铁律 2；或使用固定管理员 Token，等于取消隔离。

**Dify 的适用条件：** 仅当运营团队需要脱离研发自行修改话术与流程时，才值得自部署（可并入现有 `docker-compose.yml`）。即便如此，数据仍须由 NestJS 注入，Dify 不得直连数据库。

**大模型仍然使用外部 API**（DeepSeek / 豆包，经火山方舟 OpenAI 兼容接口）。被否决的是「外部平台充当数据通路」，不是「外部模型」。`DeepseekService.completeJson()` 继续复用，无需更换。

### A.1 为什么用 JSON 意图而非原生 `tool_calls`

小参数量模型（豆包 Lite、DeepSeek Flash）在多工具场景下选择错误率偏高，且选择过程不可见。要求模型输出固定结构的意图 JSON，可由后端直接落日志、可逐条回归测试，出错时能定位到具体枚举误判。工具数量超过 10 个或需要单轮串联多工具时，再评估升级为原生 function calling。

### A.2 主循环参考实现

```ts
async chat(message: string, user: JwtPayload, sessionId?: string) {
  const plan = await this.deepseek.completeJson(INTENT_PROMPT, message)
                    .catch(() => matchByKeyword(message));

  if (plan.intent === 'write_request') return refuseWrite();

  const facts = await this.tools.run(plan.intent, plan.params, user.merchantId);
  const answer = renderTemplate(plan.intent, facts)
              ?? await this.narrate(plan.intent, facts);

  await this.log({ provider: 'chat', purpose: plan.intent, merchantId: user.merchantId, ... });
  return { sessionId, answer, intent: plan.intent, facts };
}
```

模型在此链路中被调用两次，两次均不接触租户标识，均不执行算术运算。
